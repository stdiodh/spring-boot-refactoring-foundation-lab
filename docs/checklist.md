# 리팩토링 체크리스트

## 1. 기능 확인

- [ ] 리팩토링 전 `./gradlew test` 결과를 확인했습니다.
- [ ] 리팩토링 후 `./gradlew test`가 다시 통과합니다.
- [ ] API path, status code, response body를 임의로 바꾸지 않았습니다.

## 2. 코드 구조 확인

- [ ] `post`, `auth`, `account/recovery` 책임을 기능 단위로 찾을 수 있습니다.
- [ ] `common`에는 여러 기능이 함께 쓰는 책임만 남겼습니다.
- [ ] package 선언과 import가 이동한 경로와 일치합니다.

## 3. 실패 케이스 확인

- [ ] 패키지 이동 실패와 책임 분리 실패를 구분할 수 있습니다.
- [ ] 테스트 실패가 어느 변경 이후 생겼는지 설명할 수 있습니다.
- [ ] 기능 동작 변경이 필요한 경우 리팩토링 범위를 넘는 변경으로 따로 기록했습니다.

## 4. 설명할 수 있어야 하는 것

- [ ] 리팩토링이 동작 변경과 다른 이유를 설명할 수 있습니다.
- [ ] feature-based 구조를 선택한 이유를 설명할 수 있습니다.
- [ ] `common` 패키지를 좁게 유지해야 하는 이유를 설명할 수 있습니다.

## 5. 남은 한계와 다음 시퀀스 연결

- [ ] 이번 단계가 대규모 아키텍처 개편이 아니라 구조 기초 보강임을 구분합니다.
- [ ] 다음 시퀀스의 이벤트 기반 흐름은 정리된 책임 경계 위에서 이해합니다.
