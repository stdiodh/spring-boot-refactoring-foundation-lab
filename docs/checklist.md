# 리팩토링 체크리스트

## 1. 기능 확인

- [ ] 리팩토링 전 `./gradlew test` 결과를 확인했습니다.
- [ ] 리팩토링 후 `./gradlew test`가 다시 통과합니다.
- [ ] API path, status code, response body를 임의로 바꾸지 않았습니다.

## 2. 코드 구조 확인

- [ ] `AuthService`는 입력 정리, 조회, 비밀번호 검증, token 응답 책임을 구분합니다.
- [ ] `PostService`는 필드 검증, Entity 조작, 응답 변환 책임을 구분합니다.
- [ ] `GlobalExceptionHandler`는 서비스 검증 실패를 일관된 응답으로 변환합니다.
- [ ] 테스트는 private helper가 아니라 외부 동작을 검증합니다.

## 3. 실패 케이스 확인

- [ ] 현재 답안이 패키지 이동이 아니라 책임 분리를 구현한다는 점을 확인했습니다.
- [ ] 테스트 실패가 어느 helper/검증/예외 변경 이후 생겼는지 설명할 수 있습니다.
- [ ] 기능 동작 변경이 필요한 경우 리팩토링 범위를 넘는 변경으로 따로 기록했습니다.

## 4. 설명할 내용

- [ ] 리팩토링이 동작 변경과 다른 이유를 설명할 수 있습니다.
- [ ] helper 수가 아니라 책임 경계가 리팩토링 기준인 이유를 설명할 수 있습니다.
- [ ] feature-based 구조가 이번 답안의 후속 선택지인 이유를 설명합니다.

## 5. 남은 한계와 다음 시퀀스 연결

- [ ] 이번 단계가 대규모 아키텍처 개편이 아니라 구조 기초 보강임을 확인했습니다.
- [ ] 다음 시퀀스의 이벤트 기반 흐름은 정리된 책임 경계 위에서 이해합니다.
